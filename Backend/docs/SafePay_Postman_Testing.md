# SafePay: Postman testing guide

SafePay is a simulated risk-adaptive pre-settlement transaction-control layer.

This guide describes the current backend source as of 11 September 2026. Its examples and assertions have not been executed against Oracle in this session. It does not claim a passing end-to-end run.

## Import the ready-made requests

1. Start the backend separately after confirming Oracle is available and your datasource settings are correct. Run `com.ofss.SafePayApplication` from your Java IDE, or use a working Maven installation with `mvn spring-boot:run`. The repository wrapper previously failed in this Windows environment, so it is not assumed to work.
2. Restart after the recent code changes. `spring.jpa.hibernate.ddl-auto=update` is configured to add the cancellation idempotency key and authorized/released timestamp columns. No schema changes have been run by this documentation task.
3. In Postman, choose **Import** and select both:
   - [SafePay.postman_collection.json](../postman/SafePay.postman_collection.json)
   - [SafePay.local.postman_environment.json](../postman/SafePay.local.postman_environment.json)
4. Select **SafePay Local** as the active environment. Its `baseUrl` defaults to `http://localhost:8080`.
5. Use **No Auth**. The current code has no login, JWT, or session authentication.
6. Open folder **01 Setup** and send its five requests in order. The first request creates a unique synthetic email and mobile number, then sets stable operation keys. Responses save the generated IDs automatically.
7. Send folder **02 Transfers** in order. Keep MEDIUM initiation and cancellation adjacent, within **10 seconds**. After HIGH initiation, send the polling request until its state is **SETTLED**, normally around 60–65 seconds after initiation, potentially longer under load.
8. Continue with folders **03**, **04**, and the optional **05**. Folder 05 creates separate scratch records for successful deletion examples.

Postman supports importing collection/environment files and cURL commands. The request assertions and ID capture scripts are supplied in the collection. See [Postman's import instructions](https://learning.postman.com/docs/getting-started/importing-and-exporting/importing-data/) and [post-response script documentation](https://learning.postman.com/docs/tests-and-scripts/write-scripts/test-scripts).

**Run behavior:** manual Send in the documented order is the clearest first check. On an unexpected HTTP status the scripts stop a Collection Runner run. The HIGH polling request also stops a runner if the payment is still PROTECTED; wait and send it again, then continue manually. There is no hidden sleep and no automatic payment release from Postman. Do not run the full collection unattended and assume the timer-dependent assertions passed.

## Variables and retry behavior

| Variable | How it is supplied |
|---|---|
| `baseUrl` | Environment default `http://localhost:8080`; change if your port differs |
| `testPassword` | Synthetic demonstration password in the environment; not a real account secret |
| `userEmail`, `userPhone`, `runTag` | Generated once by the first registration request for that run |
| `userId` | Captured from registration |
| `accountId` | Captured from the email-filtered account list |
| `beneficiaryId` | Captured from beneficiary creation |
| `lowTransactionId`, `mediumTransactionId`, `highTransactionId`, `hardTransactionId` | Separate IDs captured from their respective initiation requests |
| `lowKey`, `mediumKey`, `highKey`, `hardKey` | Stable per-payment keys generated during setup |
| `mediumCancelKey` | Stable key for cancelling the MEDIUM payment |
| `scratchEmail`, `scratchPhone` | Generated by the first setup request for the separate deletion examples |
| `extraAccountId`, `scratchUserId`, `scratchAccountId` | Captured only for optional CRUD/deletion examples |

Use the selected environment consistently. A successful response saves IDs; do not guess sequence values.

An **identical retry** uses the same key and original body. A **new payment** needs a new key. Do not use `{{$guid}}` directly as a header on every send, since that makes retries look like new payments. Change the relevant key variable to create another payment, or begin a fresh run by sending the first registration again. That first registration resets all working IDs and keys.

The MEDIUM window can expire while manually switching tabs. If cancellation returns 400 for expiry, that is expected server behavior. Restart from folder 01 setup to reproduce the clean balance/history scenario. Creating a replacement MEDIUM payment alone leaves the old payment to settle, so the documented balances would no longer apply.

## What to observe in the main flow

| Step completed | Account balance | Pending reservations | Spendable after INR 5,000 minimum |
|---|---:|---:|---:|
| Register | 5000 | 0 | 0 |
| Set balance | 500000 | 0 | 495000 |
| LOW 10000 settles | 490000 | 0 | 485000 |
| MEDIUM 25000 protected | 490000 | 25000 | 460000 |
| MEDIUM cancelled | 490000 | 0 | 485000 |
| HIGH 75000 protected | 490000 | 75000 | 410000 |
| HIGH settles | 415000 | 0 | 410000 |
| HARD_HOLD 150000 | 415000 | 150000 | 260000 |

The account endpoint returns the posted balance, not reserved/spendable fields. Reservations are the sum of PROTECTED and HARD_HOLD transaction amounts. Cancellation frees a reservation; it does not refund a debit because the debit has not happened yet.

The clean final history contains four payments: **two SETTLED, one CANCELLED, one HARD_HOLD**. The HARD_HOLD payment remains pending because there is no authentication/release endpoint yet. The scheduler never releases it.

## Request format

For JSON requests, use **Body > raw > JSON** and `Content-Type: application/json`.

- Transaction initiation/cancellation and beneficiary creation/status updates take details in JSON.
- Resource IDs remain in paths where shown.
- Initiation and cancellation require the `Idempotency-Key` header.
- GET requests have **no body**; use their listed query parameters.
- Account creation is still `POST /accounts?userId=...` with JSON balance.
- Transaction history filtering uses **state**, not status.
- The account prefix is **/accounts**, not /api/accounts.
- There is no POST /api/auth/login endpoint.

An initiation body is:

```json
{
  "fromAccountId": {{accountId}},
  "beneficiaryId": {{beneficiaryId}},
  "amount": 25000.00,
  "purpose": "Demo payment",
  "userEmail": "{{userEmail}}"
}
```

For the four risk scenarios, use amounts 10000, 25000, 75000, and 150000 with their distinct stable keys. With two-decimal currency values, 10000.01 is MEDIUM, 50000.01 is HIGH, and 100000.01 is HARD_HOLD.

## cURL commands to import into Postman

These snippets use Postman `{{variables}}`. Paste a snippet into **Import > raw text**; Postman resolves variables from the selected environment when sending. These placeholders are not PowerShell variables and will not resolve by pasting directly into a terminal.

If you import a single cURL snippet instead of the collection, initialize its variables yourself and copy returned IDs manually. A cURL import does not carry the collection's capture/test scripts. For registration, a synthetic example is userEmail=`asha.safepay.demo@example.com`, userPhone=`9876543210`, testPassword=`SafePayDemo!123`; change both email and phone if already used.

Use the commands below when their setup prerequisites are satisfied. The cancellation example targets the MEDIUM payment; the deletion examples target unused/scratch records, never the main history-bearing account.

### 1. Registration through /api/auth

Expected HTTP 201. In the imported collection, run this first: its pre-request script creates a NEW synthetic user and resets working IDs/keys on each Send. A single cURL import does not include that script. Later requests reuse those keys; retry tests do not generate new keys. Registration also creates an INR 5,000 account. Account ID must be discovered in the next request.

```bash
curl --request POST "{{baseUrl}}/api/auth/register" \
  --header "Content-Type: application/json" \
  --data-raw '{
  "name": "Postman Customer",
  "email": "{{userEmail}}",
  "phone": "{{userPhone}}",
  "password": "{{testPassword}}"
}'
```

### 2. Find the automatically created account

Expected HTTP 200. Filtered by the new unique email. Captures accountId; no sequence values are assumed.

```bash
curl --request GET "{{baseUrl}}/accounts?userEmail={{userEmail}}"
```

### 3. Set the simulated account balance

Expected HTTP 200. Replaces the simulator balance. This is not a bank deposit endpoint. Use the fresh account from setup.

```bash
curl --request PUT "{{baseUrl}}/accounts/{{accountId}}" \
  --header "Content-Type: application/json" \
  --data-raw '{
  "balance": 500000
}'
```

### 4. Add a beneficiary

Expected HTTP 200. All creation details are JSON. New beneficiary is ACTIVE. Repeating this exact creation for the same account should conflict.

```bash
curl --request POST "{{baseUrl}}/api/beneficiaries" \
  --header "Content-Type: application/json" \
  --data-raw '{
  "accountId": {{accountId}},
  "userEmail": "{{userEmail}}",
  "beneficiaryName": "Demo Payee",
  "bankAccountNumber": "123456789012",
  "ifsc": "SBIN0001234"
}'
```

### 5. List beneficiaries

Expected HTTP 200.

```bash
curl --request GET "{{baseUrl}}/api/beneficiaries?userEmail={{userEmail}}"
```

### 6. Initiate a LOW payment

Expected HTTP 200. Amount INR 10000; expected LOW/SETTLED. The key lowKey is stable for retries. Change it for a genuinely new payment.

```bash
curl --request POST "{{baseUrl}}/api/transactions/initiate" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: {{lowKey}}" \
  --data-raw '{
  "fromAccountId": {{accountId}},
  "beneficiaryId": {{beneficiaryId}},
  "amount": 10000,
  "purpose": "Postman payment",
  "userEmail": "{{userEmail}}"
}'
```

### 7. Cancel a protected payment

Expected HTTP 200. Send immediately after folder 02 request 05 (MEDIUM initiation). If the 10-second window is missed, a 400 is correct; restart folder 01 setup to reproduce the clean balance/history scenario.

```bash
curl --request POST "{{baseUrl}}/api/transactions/{{mediumTransactionId}}/cancel" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: {{mediumCancelKey}}" \
  --data-raw '{
  "userEmail": "{{userEmail}}"
}'
```

### 8. Get transaction details / poll status

Expected HTTP 200. Wait about 65 seconds from HIGH initiation, then Send. Repeat until state=SETTLED. This request does not cause settlement; the backend's five-second scheduled job does. Do not use an initiation retry as polling.

```bash
curl --request GET "{{baseUrl}}/api/transactions/{{highTransactionId}}?userEmail={{userEmail}}"
```

### 9. Filter transaction history

Expected HTTP 200.

```bash
curl --request GET "{{baseUrl}}/api/transactions?userEmail={{userEmail}}&state=SETTLED"
```

### 10. Change beneficiary status

Expected HTTP 200.

```bash
curl --request PATCH "{{baseUrl}}/api/beneficiaries/{{beneficiaryId}}/status" \
  --header "Content-Type: application/json" \
  --data-raw '{
  "status": "INACTIVE",
  "userEmail": "{{userEmail}}"
}'
```

### 11. List users

Expected HTTP 200.

```bash
curl --request GET "{{baseUrl}}/api/users"
```

### 12. Get user details

Expected HTTP 200.

```bash
curl --request GET "{{baseUrl}}/api/users/{{userId}}"
```

### 13. Update user details

Expected HTTP 200. Password omitted, so existing password hash remains. Supply password in JSON only when changing it.

```bash
curl --request PUT "{{baseUrl}}/api/users/{{userId}}" \
  --header "Content-Type: application/json" \
  --data-raw '{
  "name": "Updated Postman Customer",
  "email": "{{userEmail}}",
  "phone": "{{userPhone}}"
}'
```

### 14. Create another account

Expected HTTP 200. This endpoint still takes userId in the query string and balance in JSON.

```bash
curl --request POST "{{baseUrl}}/accounts?userId={{userId}}" \
  --header "Content-Type: application/json" \
  --data-raw '{
  "balance": 10000
}'
```

### 15. Get account details

Expected HTTP 200. If MEDIUM was cancelled and HIGH settled, the posted balance is 415000. HARD_HOLD reserves 150000 without a debit; spendable funds are 260000. Reservation/available amounts are not response fields.

```bash
curl --request GET "{{baseUrl}}/accounts/{{accountId}}"
```

### 16. Delete an unused additional account

Expected HTTP 200. Deletes only the account just created in folder 05 request 05; it has no beneficiaries or transaction history. Expected 200 with empty body.

```bash
curl --request DELETE "{{baseUrl}}/accounts/{{extraAccountId}}"
```

### 17. Registration alias through /api/users

Expected HTTP 201. Separate synthetic customer for delete tests; does not replace the main userId.

```bash
curl --request POST "{{baseUrl}}/api/users" \
  --header "Content-Type: application/json" \
  --data-raw '{
  "name": "Scratch Customer",
  "email": "{{scratchEmail}}",
  "phone": "{{scratchPhone}}",
  "password": "{{testPassword}}"
}'
```

### 18. Delete the scratch user after its accounts

Expected HTTP 204.

```bash
curl --request DELETE "{{baseUrl}}/api/users/{{scratchUserId}}"
```

## Error responses and edge cases

| Condition | Expected behavior |
|---|---|
| Missing required JSON field, invalid IFSC/email/mobile, nonpositive amount, more than two decimal places |400 |
| Insufficient spendable funds after pending holds |400 |
| Account balance update below reservations +5000 |400 |
| Cancel SETTLED, HARD_HOLD, or an expired protection window |400 |
| Identical initiation retry |200, same transaction ID; state may have advanced |
| Same initiation key with different amount/account/beneficiary/purpose |409 |
| Identical cancellation retry |200, same CANCELLED payment |
| Cancellation key reused for a different transaction |409 |
| Duplicate email/phone or beneficiary tuple |409 |
| Missing resource / incorrect owner context |404 in ordinary resource lookups |
| Dependency-protected account/user deletion |400 |

Validation errors use an `errors` object with field names. Other handled errors usually contain a `message`. DELETE account returns 200 with an empty body; DELETE user returns 204 with an empty body. Do not call `pm.response.json()` for these responses.

An example response shape, with generated values shown illustratively, is:

```json
{
  "transactionId": 42,
  "transactionRef": "TXN-<generated UUID>",
  "state": "PROTECTED",
  "riskTier": "MEDIUM",
  "protectionExpiresAt": "2026-09-11T12:00:10",
  "riskReason": "Amount is within the Medium-risk range.",
  "amount": 25000.00,
  "purpose": "Demo payment",
  "fromAccountId": 1000001,
  "beneficiaryId": 1,
  "beneficiaryName": "Demo Payee",
  "createdAt": "2026-09-11T12:00:00",
  "authorizedAt": "2026-09-11T12:00:00",
  "releasedAt": null,
  "settledAt": null,
  "cancelledAt": null,
  "protectionSeconds": 10,
  "authenticationRequired": false
}
```

For LOW/HARD_HOLD, protectionExpiresAt is an empty string. The timestamps are serialized without a timezone offset; use returned transaction state as the authoritative result rather than guessing expiry from your workstation timezone.
