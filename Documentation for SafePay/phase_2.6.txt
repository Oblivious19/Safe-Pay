## Phase 2.6 objective

Phase 2.6 builds the canonical payment instruction and centralized transaction state engine.

The major outcomes will be:

- A `PAYMENT_TRANSACTION` JPA model with optimistic locking.
- Append-only `TRANSACTION_RISK_FACTOR` evidence.
- Strict customer/account/beneficiary ownership.
- Separate transaction creation and authorization operations.
- Atomic risk assessment, policy-snapshot persistence and fund reservation.
- Tier-specific routing into `RELEASED`, `PROTECTED`, or `VERIFICATION_REQUIRED`.
- Central enforcement of every allowed and forbidden state transition.
- Ownership-scoped transaction retrieval and risk explanations.
- Customer cancellation before release.
- REST endpoints using DTOs rather than entity serialization.

## Canonical state engine

The complete state vocabulary will be:

```text
CREATED
AUTHORIZED
RISK_ASSESSED
PROTECTED
VERIFICATION_REQUIRED
PENDING_RISK_REVIEW
RELEASED
SETTLED
CANCELLED
FAILED
```

Core routing after authorization:

```text
LOW         → RELEASED
MEDIUM/HIGH → PROTECTED
VERY_HIGH   → VERIFICATION_REQUIRED
```

The full transition matrix will exist centrally so future OTP, review, scheduler and settlement phases can reuse it without duplicating transition logic.

## Important Phase 2.6 invariants

- Creation and authorization remain separate operations.
- Creation performs no risk assessment, reservation, release or settlement.
- Customers cannot submit a risk tier, policy identity or transaction state.
- Authorization revalidates customer, account, beneficiary, amount and current state.
- The complete Phase 2.5 result is persisted as one coherent snapshot.
- `riskScore` remains null for V1.
- `TransactionRiskFactor` records only the approved `PAYMENT_AMOUNT` evidence.
- MEDIUM and HIGH receive server-calculated deadlines.
- VERY_HIGH never receives a timer.
- Reservation and state routing occur in one transaction.
- Terminal states never reopen.
- Cross-customer access must appear as resource-not-found.
- Concurrent modifications are detected through `VERSION_NO`.
- No controller will reproduce risk-band or state-transition logic.

## Explicit later-phase boundaries

Phase 2.6 will prepare the state and persistence foundations but will not improperly absorb:

- Phase 2.7 — durable idempotency processing.
- Phase 2.8 — scheduled expiry and final Undo-versus-release race hardening.
- Phase 2.9 — double-entry ledger settlement and transaction exceptions.
- Phase 2.10 — OTP verification.
- Phase 2.11 — Risk Officer review decisions.
- Phase 2.12 — durable audit, notifications and WebSocket events.
- Deferred security phase — final JWT/RBAC enforcement.

For example, Phase 2.6 can route a LOW transaction safely into reservation-bearing `RELEASED`; Phase 2.9 will later perform its atomic double-entry simulated settlement and move it to `SETTLED`. That preserves the approved development order without pretending settlement already exists.

The clean batching arrangement is **2.6A–C**, then **2.6D–F**, then **2.6G–I**, with separate and combined test gates after every authorized batch.
