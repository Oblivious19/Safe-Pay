## Phase 2.9 — Ledger Settlement and Exception Recording

This phase converts an eligible `RELEASED` SafePay transaction into an internally simulated, double-entry `SETTLED` payment.

### Canonical settlement result

```text
Customer source account      DEBIT   payment amount
SafePay outbound clearing    CREDIT  payment amount
                              ----------------------
Total debits = total credits
```

The clearing credit represents simulated outbound submission. It does not claim the external beneficiary received money.

### Principal components

- `LedgerPosting` header representing one complete settlement group.
- `LedgerEntry` immutable debit/credit lines.
- `LedgerEntryType`, posting type and posting-status enums.
- `TransactionExceptionLog` and its processing-stage/status enums.
- Ledger and exception repositories with no ledger update/delete operations.
- `LedgerService` and atomic settlement worker.
- Released-transaction settlement processor.
- Deterministic posting identity and duplicate-settlement prevention.
- Separate failure-recording transaction.
- Clearing-account configuration and validation.
- Minimal internal settlement audit/notification recording, with full APIs and WebSockets remaining in Phase 2.12.

### Non-negotiable Phase 2.9 guarantees

- Settlement accepts only `RELEASED`.
- Source and clearing accounts are locked in consistent lower-ID-first order.
- Source current and reserved balances decrease together.
- Clearing current balance increases by exactly the same amount.
- A successful posting contains exactly two different accounts and balanced amounts.
- `LEDGER_ENTRY` remains immutable.
- One transaction can have only one settlement posting group.
- Cancellation and failed payments receive no completed settlement ledger pair.
- Temporary failure retains `RELEASED` and its reservation for retry.
- Definitive failure releases the reservation and produces `FAILED`.
- No partial account update, ledger line or `SETTLED` state may survive rollback.

## Phase 2.10 — OTP Verification

This phase implements the VERY_HIGH-risk customer-verification step:

```text
VERIFICATION_REQUIRED
        |
        +-- successful OTP --> PENDING_RISK_REVIEW
        |
        +-- exhausted policy --> CANCELLED
```

The transaction remains reserved throughout successful OTP verification and later Risk Officer review.

### Approved V1 OTP policy

| Policy | V1 value |
|---|---:|
| Format | 6 numeric digits |
| Validity | 5 minutes |
| Failed attempts | Maximum 3 |
| Resend cooldown | 30 seconds |
| Issue limit | Initial issue plus two resends |
| Storage | Secure hash only |
| Successful reuse | Prohibited |
| Previous OTP after resend | Immediately invalid |
| Exhausted policy | Cancel transaction and release reservation |

### Principal components

- `OtpChallenge` mapped to `PAYMENT_OTP_CHALLENGE`.
- `OtpChallengeStatus`: `PENDING`, `VERIFIED`, `EXPIRED`, `LOCKED`, `CANCELLED`.
- `OtpChallengeDao` with locked ownership-qualified queries.
- `OtpService` for issue, resend and verification.
- Cryptographically secure six-digit generation.
- Secure hashing and verification.
- Development-only delivery-provider abstraction.
- Issue, verification and safe response DTOs.
- `VerificationController`.
- Existing `OTP_ISSUE`, `OTP_VERIFY` and `OTP_RESEND` idempotency scopes.
- Reservation release and terminal state handling when the OTP policy is exhausted.

## Decisions required before implementation

Four details are not fully fixed by the authoritative documents. I will not silently invent them:

1. **Clearing-account resolution**

   Recommendation: use an externally configured `outbound-clearing-account-id`, then validate that it identifies an active INR `OUTBOUND_CLEARING` account. Never select an arbitrary “first” clearing account.

2. **Settlement processing and retry timing**

   A recovery processor is needed because LOW authorization, timed release and future Risk Officer approval all independently produce `RELEASED`. We need approved polling/batch and retry-backoff values before implementing it.

3. **Audit/notification phase boundary**

   Recommendation: Phase 2.9 writes the minimum append-only settlement audit and notification records required by the atomic contract. Phase 2.12 then adds querying, read-status operations, delivery and WebSocket behavior.

4. **OTP-sensitive idempotency and development delivery**

   Plain SHA-256 of a six-digit OTP would be brute-forceable if stored as an idempotency fingerprint. Recommendation: use a keyed HMAC fingerprint with an externally supplied secret, while storing the OTP itself with a secure password-style hash. The development delivery provider must also be explicitly chosen and isolated from production configuration.

These decisions should be approved before 2.9A/2.10A implementation. Existing V1–V11 tables, indexes, triggers, constraints and grants otherwise appear sufficient; no migration is currently justified.
