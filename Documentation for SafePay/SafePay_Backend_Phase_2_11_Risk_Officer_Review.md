# SafePay Backend Phase 2.11 — Risk Officer Review

## Purpose and scope

Phase 2.11 implements the human Risk Officer decision stage for a `VERY_HIGH` payment after successful OTP verification. OTP verification creates a pending review round but does not approve, release or settle the payment. An authorized Risk Officer may approve, reject or request a completely new verification cycle. The customer may still cancel while the review is pending.

This is a Risk Officer workflow for the SafePay V1 prototype. It does not claim to be a complete corporate Maker-Checker system and does not change SafePay's boundary as a simulated pre-settlement control layer.

No Flyway migration, new table, new sequence or new dependency was added. The implementation uses the existing `RISK_REVIEW`, `SEQ_RISK_REVIEW_ID`, `AUDIT_LOG`, `APP_ROLE`, `USER_ROLE` and payment/account structures established by V1–V11.

## Approved V1 review policy

| Concern | V1 decision |
|---|---|
| Open status | `PENDING` is the only open review status. |
| Terminal statuses | `APPROVED`, `REJECTED`, `REVERIFICATION_REQUESTED`, `CANCELLED`. |
| Claiming | No separate claim endpoint. The first successful decision sets the assigned officer and `claimedAt`; `claimedAt` may equal `decidedAt`. |
| Approval reason | Optional, normalized plain text, maximum 1,000 characters. |
| Reject/re-verification reason | Mandatory normalized plain text, maximum 1,000 characters. |
| Internal notes | Immutable `RISK_REVIEW_NOTE_ADDED` audit events; never stored in `decision_reason`. |
| Note eligibility | Only a pending review accepts a note. |
| Queue | Pending only, oldest first, default size 20, maximum 100; no client-controlled database sorting. |
| Detail | A Risk Officer may read pending or terminal review detail, allowing a race loser to refresh the authoritative result. |
| Decision authority | Exact `RISK_OFFICER` authority plus a live, active database role assignment. `SYSTEM_ADMIN` alone is insufficient. |
| Database change | None; the existing model is sufficient. |
| Notifications | Deferred to Phase 2.12; no new delivery or WebSocket behavior is hidden in this phase. |

## Canonical review lifecycle

```text
VERY_HIGH payment + successful OTP verification
        |
        v
PENDING_RISK_REVIEW
        |
        +---- create PENDING review round N atomically
        |
        +---- Risk Officer APPROVE
        |       review -> APPROVED
        |       payment -> RELEASED
        |       reservation retained for Phase 2.9 settlement
        |
        +---- Risk Officer REJECT
        |       review -> REJECTED
        |       reservation released
        |       payment -> CANCELLED
        |
        +---- Risk Officer REQUEST RE-VERIFICATION
        |       review -> REVERIFICATION_REQUESTED
        |       payment -> VERIFICATION_REQUIRED
        |       reservation retained
        |       a new OTP is required
        |       successful OTP creates round N + 1
        |
        +---- customer cancellation wins
                review -> CANCELLED
                reservation released
                payment -> CANCELLED
```

Every completed review round remains historical evidence. Re-verification never reopens or edits an earlier round.

## Domain and Oracle mapping

`RiskReview` maps the existing Oracle object without renaming physical columns:

- `approval_id` remains the review primary key and is generated by `SEQ_RISK_REVIEW_ID`;
- `(transaction_id, review_round)` remains unique;
- the V9 function-based unique index permits at most one `PENDING` review per transaction;
- `customer_user_id` is retained independently and is protected by the V10 transaction/customer ownership relationship;
- officer assignment, deciding actor, reason, claim/decision/update times and `version_no` are mapped exactly;
- `TRG_RISK_REVIEW_FINAL_LOCK` prevents update or deletion of completed rounds;
- `@Version` supplements, rather than replaces, explicit pessimistic mutation locks.

The Java status enum is exactly:

```text
PENDING
APPROVED
REJECTED
REVERIFICATION_REQUESTED
CANCELLED
```

No invented `IN_REVIEW`, `ESCALATED` or `VERIFICATION_REQUESTED` review status is used. `VERIFICATION_REQUIRED` belongs to the payment state machine, not the review vocabulary.

## Main production components

### Domain, repository and projections

- `RiskReview` owns legal round creation and terminal mutations.
- `RiskReviewStatus` supplies the approved vocabulary and terminal-state classification.
- `RiskReviewDao` exposes only required saves, locked reads, pending lookup, newest-round lookup, queue and detail access. It deliberately exposes no delete operation.
- `RiskReviewSummaryResponse` and `RiskReviewDetailResponse` expose safe officer data with masked customer email and source account number.
- Queue mapping includes risk explanation, policy version, amount, tier, verification evidence and beneficiary context without exposing OTP material.

### Workflow and audit

- `RiskReviewServiceImpl` validates the officer against both the authenticated identity passed by the controller and the current database role assignment.
- `OtpServiceImpl` creates the next pending review inside the same transaction that marks the OTP verified and changes the payment to `PENDING_RISK_REVIEW`.
- `TransactionServiceImpl` closes a pending review when customer cancellation wins.
- `RiskReviewAuditServiceImpl` appends decision and note evidence through the existing immutable `AUDIT_LOG`.
- `AuditLog.userRiskReviewEvent` records the user actor, `RISK_OFFICER` role, review and transaction identity, action, prior/resulting payment state, outcome, reason code, correlation ID, idempotency key, timestamp and structured details.

### REST boundary

- `RiskReviewController` exposes only the approved six endpoints.
- `RiskReviewDecisionRequest` supports the optional approval reason.
- `RequiredRiskReviewDecisionRequest` requires a nonblank reject/re-verification reason.
- `RiskReviewNoteRequest` requires a nonblank internal note.
- `RiskReviewNoteResponse` acknowledges only review ID, transaction ID, event reference and recording time; it does not echo the internal note.
- `GlobalExceptionHandler` returns a safe `403 ACCESS_DENIED` response for authority failure.

## Round creation and re-verification

Round creation is part of successful OTP verification:

1. lock the owned transaction;
2. verify and terminalize the OTP challenge;
3. record verification completion;
4. transition to `PENDING_RISK_REVIEW`;
5. lock/check existing review rounds;
6. reject any already-pending review;
7. calculate `max(review_round) + 1`, defaulting to 1;
8. insert and flush the new pending round;
9. commit all changes together.

When re-verification is requested, the current review becomes `REVERIFICATION_REQUESTED`, the payment returns to `VERIFICATION_REQUIRED`, and its existing reservation stays intact. The transition logic clears the old verification completion evidence. A completely new OTP challenge is required. Only successful verification creates the next pending round.

## Decision behavior

### Approval

Approval performs:

```text
review PENDING -> APPROVED
payment PENDING_RISK_REVIEW -> RELEASED
reservation remains equal to payment amount
append RISK_REVIEW_APPROVED audit event
```

Phase 2.9 later settles the released payment. Approval does not post the ledger directly.

### Rejection

Rejection performs:

```text
review PENDING -> REJECTED
release source-account reservation
end transaction reservation
payment PENDING_RISK_REVIEW -> CANCELLED
append RISK_REVIEW_REJECTED audit event
```

The funds and state changes are committed atomically with the review decision and audit evidence.

### Re-verification request

Re-verification performs:

```text
review PENDING -> REVERIFICATION_REQUESTED
payment PENDING_RISK_REVIEW -> VERIFICATION_REQUIRED
reservation retained
old verification evidence cleared by state transition
append RISK_REVIEW_REVERIFICATION_REQUESTED audit event
```

It does not resend an old OTP, generate a replacement automatically or approve the payment.

## Internal-note and audit contract

Internal notes are audit evidence, not mutable review fields:

- action code is `RISK_REVIEW_NOTE_ADDED`;
- entity type is `RISK_REVIEW` and entity ID is the review ID;
- the event also links the payment transaction;
- actor type is `USER` with actor role `RISK_OFFICER`;
- previous and resulting payment state both remain `PENDING_RISK_REVIEW`;
- the note is held in immutable `details_json` and is never echoed to a customer response;
- correlation and idempotency identities are retained;
- each note receives a unique 64-character-safe event reference;
- notes are rejected after the review becomes terminal.

Officer decisions use a deterministic event reference based on the review identity. Since one review round has only one terminal officer decision, the Oracle unique event reference also provides an independent duplicate-evidence barrier.

No raw OTP, OTP digest/salt, full account number, credential or SMTP detail enters review audit evidence.

## API and authorization contract

| Method | Endpoint | Body | Success |
|---|---|---|---:|
| `GET` | `/api/v1/admin/risk-reviews?page=0&size=20` | none | `200` |
| `GET` | `/api/v1/admin/risk-reviews/{reviewId}` | none | `200` |
| `POST` | `/api/v1/admin/risk-reviews/{reviewId}/approve` | optional `reason` | `200` |
| `POST` | `/api/v1/admin/risk-reviews/{reviewId}/reject` | required `reason` | `200` |
| `POST` | `/api/v1/admin/risk-reviews/{reviewId}/request-verification` | required `reason` | `200` |
| `POST` | `/api/v1/admin/risk-reviews/{reviewId}/notes` | required `note` | `201` |

Every request requires a `SafePayPrincipal` with exact `RISK_OFFICER` authority. Every service operation repeats the live check: the officer must exist, be `ACTIVE`, and still have the canonical `RISK_OFFICER` role in `USER_ROLE`. This closes the gap where a stale authenticated session might retain an authority after role removal.

The combined demonstration administrator may use these APIs only because that persona is separately assigned `RISK_OFFICER`. Possessing `SYSTEM_ADMIN` by itself does not grant review authority.

## Idempotency and safe failures

All four state-changing POST operations require exactly one `Idempotency-Key` header and use distinct scopes:

```text
RISK_REVIEW_APPROVE
RISK_REVIEW_REJECT
RISK_REVIEW_REQUEST_VERIFICATION
RISK_REVIEW_ADD_NOTE
```

The fingerprint includes the operation, exact review-specific endpoint and normalized logical body. The same key and same fingerprint replay the stored safe response. Reusing a key for another review, action or body produces an idempotency conflict.

The success response stores the linked transaction identity in the idempotency record. Replays emit `Idempotency-Replayed: true` and do not execute the service or append a second audit event.

Safe failures include:

- `400` for malformed identifiers, paging, headers or request bodies;
- `403 ACCESS_DENIED` for insufficient authority or a non-active/non-assigned officer;
- `404 RISK_REVIEW_NOT_FOUND` without exposing internal row details;
- `409` when another action already completed the review/payment transition;
- existing safe idempotency conflict/in-progress responses.

No SQL, stack trace, internal note, credential or unmasked financial identifier is returned.

## Atomicity and concurrency guarantees

All review mutations execute in a database transaction. Competing customer/officer and officer/officer actions follow the same lock order:

```text
PAYMENT_TRANSACTION
        -> RISK_REVIEW
        -> ACCOUNT only when reservation release is required
```

This prevents inconsistent lock inversion. After acquiring the locks, the service rechecks both the review status and payment state. Therefore:

- two officers cannot produce two final decisions;
- approval cannot succeed after customer cancellation;
- customer cancellation cannot succeed after officer approval;
- rejection cannot release funds twice;
- a terminal review cannot receive another note;
- a race loser receives a state conflict and may read the terminal review detail for the authoritative result.

The Oracle one-pending-review index, review optimistic version, payment/account versions, final-row trigger and unique audit event reference remain independent defense layers.

## Oracle alignment and rollback-safe verification

- Tests use the owner connection only to create and remove static user, role, account and beneficiary fixtures.
- Production workflow calls execute through the restricted application datasource.
- Integration tests are transactionally rolled back because Oracle deliberately prohibits deletion of completed review rows.
- The terminal-row test directly attempts an illegal update and expects Oracle error `ORA-20045` from `TRG_RISK_REVIEW_FINAL_LOCK`.
- The workflow tests verify approval/audit, rejection/fund release, re-verification/round 2, internal-note evidence and competing terminal decisions.
- Schedulers are disabled for these focused tests so a newly `RELEASED` payment is not asynchronously settled before assertions.

No V1–V11 migration is edited, and no test disables or bypasses a financial constraint.

## Operational notes for teammates

1. Never interpret successful OTP verification as payment approval; it creates a pending review.
2. Never update or delete completed `RISK_REVIEW` rows manually.
3. Never bypass `RiskReviewService` to change review/payment state or release reserved funds.
4. Use a new idempotency key for a genuinely new decision/note and reuse a key only for a retry of the identical logical request.
5. A re-verification request needs a new OTP cycle and later creates a new review round; it does not reopen the prior round.
6. Internal notes are privileged audit evidence. Do not place them in customer transaction DTOs, notifications or logs.
7. Approval leaves the reservation intact because Phase 2.9 settlement consumes it.
8. Rejection and customer cancellation release the reservation exactly once.
9. After a `409`, fetch review detail and render the server's authoritative status rather than trusting stale UI state.
10. Run the focused Phase 2.11 groups, the Oracle workflow test and the complete Maven suite before locking the phase.
