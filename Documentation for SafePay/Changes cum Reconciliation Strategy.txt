##1.9F — Reconciliation strategy


I recommend additive Flyway evolution, not a prototype rebuild.

Reasons:
- V1–V8 already represent almost every approved enterprise-safe concept.
- The team schema would remove reservation, ledger, OTP, idempotency, sessions, policies, notifications and reconciliation.
- Team merits are mainly Java teaching patterns rather than superior database objects.
- The required structural changes are concentrated and can be expressed forward-only.
- Preserving migration history teaches the correct enterprise method.
- A destructive rebuild provides little benefit and introduces unnecessary risk.

The eventual sequence should be:
1. Approve the Phase 1.9 decision matrix.
2. Prepare exact manual amendments for the Decision Register and implementation plan.
3. Design a forward reconciliation migration for names, text policy version, review statuses and approved integrity improvements.
4. Design canonical reference and seed data separately.
5. Validate the complete empty-schema migration path.
6. Revalidate runtime grants, constraints, triggers and views.
7. Begin backend mapping in small teaching phases, adapting selected team code rather than copying it wholesale.
